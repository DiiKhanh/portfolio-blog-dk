# Go Concurrency Patterns Explained

Go's concurrency model is one of its defining features. Instead of threads with locks, Go gives you goroutines and channels — lightweight primitives that make concurrent code easier to write and reason about.

> "Do not communicate by sharing memory; instead, share memory by communicating." — Rob Pike

## Goroutines

A goroutine is a lightweight thread managed by the Go runtime. Starting one is as simple as adding the `go` keyword:

```go
package main

import (
    "fmt"
    "time"
)

func greet(name string) {
    fmt.Printf("Hello, %s!\n", name)
}

func main() {
    go greet("Alice") // runs concurrently
    go greet("Bob")   // runs concurrently
    go greet("Carol") // runs concurrently

    // Main goroutine continues here
    time.Sleep(100 * time.Millisecond) // wait for goroutines to finish
    fmt.Println("Done")
}
```

> Using `time.Sleep` to wait is bad practice. We'll fix this with `sync.WaitGroup` below.

Goroutines are cheap — you can run tens of thousands concurrently. They start with ~2KB of stack (vs ~1MB for OS threads) and grow as needed.

## Channels

Channels are how goroutines communicate. Think of them as typed pipes:

```go
// Create a channel for integers
ch := make(chan int)

// Send value into the channel (in a goroutine)
go func() {
    ch <- 42 // send
}()

value := <-ch // receive — blocks until a value arrives
fmt.Println(value) // 42
```

### Buffered vs Unbuffered Channels

An **unbuffered** channel (the default) blocks the sender until the receiver is ready:

```go
ch := make(chan string) // unbuffered
```

A **buffered** channel allows sending up to `n` values without blocking:

```go
ch := make(chan string, 3) // buffered, capacity 3
ch <- "first"  // doesn't block
ch <- "second" // doesn't block
ch <- "third"  // doesn't block
ch <- "fourth" // blocks! buffer is full
```

### Closing Channels

Close a channel to signal that no more values will be sent:

```go
func producer(ch chan<- int) {
    for i := 0; i < 5; i++ {
        ch <- i
    }
    close(ch) // signal completion
}

func main() {
    ch := make(chan int)
    go producer(ch)

    // Range over channel until it's closed
    for v := range ch {
        fmt.Println(v) // 0, 1, 2, 3, 4
    }
}
```

Only the **sender** should close a channel. Closing from the receiver side causes a panic.

## sync.WaitGroup

`WaitGroup` is the idiomatic way to wait for multiple goroutines to finish:

```go
package main

import (
    "fmt"
    "sync"
)

func worker(id int, wg *sync.WaitGroup) {
    defer wg.Done() // decrement counter when done
    fmt.Printf("Worker %d starting\n", id)
    // ... do work ...
    fmt.Printf("Worker %d done\n", id)
}

func main() {
    var wg sync.WaitGroup

    for i := 1; i <= 5; i++ {
        wg.Add(1)         // increment counter before starting goroutine
        go worker(i, &wg) // pass pointer to WaitGroup
    }

    wg.Wait() // block until counter reaches zero
    fmt.Println("All workers done")
}
```

**Common mistake:** calling `wg.Add(1)` inside the goroutine — there's a race condition between the goroutine starting and `wg.Wait()` checking.

## Select Statement

`select` lets you wait on multiple channel operations at once:

```go
func main() {
    ch1 := make(chan string)
    ch2 := make(chan string)

    go func() {
        time.Sleep(1 * time.Second)
        ch1 <- "one"
    }()

    go func() {
        time.Sleep(2 * time.Second)
        ch2 <- "two"
    }()

    for i := 0; i < 2; i++ {
        select {
        case msg := <-ch1:
            fmt.Println("Received from ch1:", msg)
        case msg := <-ch2:
            fmt.Println("Received from ch2:", msg)
        }
    }
}
```

### Timeout with Select

```go
select {
case result := <-dataCh:
    fmt.Println("Got result:", result)
case <-time.After(5 * time.Second):
    fmt.Println("Timed out!")
}
```

### Non-Blocking with Default

```go
select {
case msg := <-ch:
    fmt.Println("Received:", msg)
default:
    fmt.Println("No message — continuing")
}
```

## Fan-Out / Fan-In

A powerful pattern for parallel processing:

```go
// Fan-out: send work to N workers
func fanOut(jobs <-chan int, numWorkers int) []<-chan int {
    outputs := make([]<-chan int, numWorkers)
    for i := 0; i < numWorkers; i++ {
        results := make(chan int)
        outputs[i] = results
        go func(out chan<- int) {
            for job := range jobs {
                out <- job * job // process job
            }
            close(out)
        }(results)
    }
    return outputs
}

// Fan-in: merge multiple channels into one
func fanIn(channels ...<-chan int) <-chan int {
    merged := make(chan int)
    var wg sync.WaitGroup

    for _, ch := range channels {
        wg.Add(1)
        go func(c <-chan int) {
            defer wg.Done()
            for v := range c {
                merged <- v
            }
        }(ch)
    }

    go func() {
        wg.Wait()
        close(merged)
    }()

    return merged
}
```

## Cancellation with Context

Use `context.Context` to cancel goroutines gracefully:

```go
func worker(ctx context.Context, id int) {
    for {
        select {
        case <-ctx.Done():
            fmt.Printf("Worker %d: cancelled\n", id)
            return
        default:
            fmt.Printf("Worker %d: working...\n", id)
            time.Sleep(500 * time.Millisecond)
        }
    }
}

func main() {
    ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
    defer cancel()

    var wg sync.WaitGroup
    for i := 1; i <= 3; i++ {
        wg.Add(1)
        go func(id int) {
            defer wg.Done()
            worker(ctx, id)
        }(i)
    }

    wg.Wait()
    fmt.Println("All workers stopped")
}
```

## Mutex for Shared State

When goroutines must share data (not via channels), use `sync.Mutex`:

```go
type SafeCounter struct {
    mu    sync.Mutex
    count int
}

func (c *SafeCounter) Increment() {
    c.mu.Lock()
    defer c.mu.Unlock()
    c.count++
}

func (c *SafeCounter) Value() int {
    c.mu.Lock()
    defer c.mu.Unlock()
    return c.count
}

func main() {
    counter := &SafeCounter{}
    var wg sync.WaitGroup

    for i := 0; i < 1000; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            counter.Increment()
        }()
    }

    wg.Wait()
    fmt.Println("Final count:", counter.Value()) // always 1000
}
```

## Common Pitfalls

### Goroutine Leak

A goroutine that's stuck waiting on a channel that nobody will ever send to is a leak:

```go
// ❌ Goroutine leaks if nobody reads from results
func process() <-chan int {
    results := make(chan int)
    go func() {
        results <- expensiveComputation() // stuck here if caller ignores channel
    }()
    return results
}

// ✅ Accept a context for cancellation
func process(ctx context.Context) <-chan int {
    results := make(chan int, 1) // buffered — won't block if nobody reads
    go func() {
        select {
        case results <- expensiveComputation():
        case <-ctx.Done():
        }
    }()
    return results
}
```

## Key Takeaways

- Goroutines are cheap — spin up thousands without worry
- **Unbuffered channels** synchronize sender and receiver; **buffered** channels decouple them
- Only the sender should `close()` a channel
- Use `sync.WaitGroup` to wait for a group of goroutines
- Use `select` to handle multiple channels simultaneously — add `default` for non-blocking
- Prefer passing data through channels over sharing memory with mutexes
- Always handle cancellation with `context.Context` to prevent goroutine leaks

Concurrency in Go is genuinely fun once the mental model clicks. Start with goroutines + channels for communication, and only reach for mutexes when you must share state.
